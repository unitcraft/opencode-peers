# Задание: шаги приёмки проекта берутся из документа Канона проекта, а не из текстов в настройках

Заказчик и владелец: владелец репозитория `unitcraft/crew-harness` (он же отвечает на вопросы и принимает результат).
Репозиторий кода: `unitcraft/crew-harness` (https://github.com/unitcraft/crew-harness, ветка `main`). Дата задания: 2026-10-11.
Источник: наблюдение 2026-10-11 в проекте-потребителе: тексты шагов `ci` и `gate` в настройках описывали старый порядок приёмки и расходились с плагином и с практикой.

Задача полная: разбор, план, реализация, сдача.

## Чего хочет владелец (его слова, 2026-10-11)

- «разве acceptance проекта не должен формироваться на основе канона?»
- «я не хочу две правды, должно быть одно окно, мне так кажется» — и «по рекомендации»: источник один.
- «правило записанное словами не выполняется» (2026-10-10): две копии одного правила расходятся.

## Что есть сейчас

- Шаги приёмки проекта (`id`, `text`, `required`) записаны текстами в настройках (`acceptance`, `opencode-plugin/core.ts`, `config-schema.ts`). Их смысл ссылается на документы Канона проекта и повторяет его, то есть копия, которая расходится с оригиналом.
- В запись задачи шаги копируются при начале приёмки (`t.steps`), исполнителю показываются в письме с задачей (`acceptanceForExecutor`), приёмщик пишет результат по шагу (`crew_task check`, `checks`).
- Порядок посадки (precheck, замок, accept) задаёт плагин (`merge_precheck`, `accepted_slot`), `crew_doctor` предупреждает, когда текст шага описывает порядок (коммит доктора, 2026-10-11).

## Что нужно

- Один источник шагов: документ Канона проекта. В настройках появляется ключ `acceptance_file` (путь внутри репозитория проекта) с таблицей критериев: `id`, текст, обязателен (формат таблицы определяет разбор; он должен читаться и человеком, и плагином).
- Плагин читает файл с целевой ветки (`git show origin/<целевая>:<файл>`; кеш на проход, без блокировки главного потока службы), строит список шагов и дальше работает как сейчас (копия в запись задачи, письмо исполнителю, `checks`).
- Если заданы и `acceptance_file`, и `acceptance` с текстами: `crew_doctor` показывает ошибку, плагин берёт файл Канона. Проект без `acceptance_file` продолжает работать с `acceptance` (переходный период), после переноса проектами ключ `acceptance` из схемы убирается отдельным решением.
- Недоступный файл (нет в ветке, нет сети): откат к `acceptance` из настроек с предупреждением; без обоих — прежнее поведение «шагов нет».
- Порядок приёмки в таблицу не копируется (он в плагине и справке `crew_help`); справка говорит это одним предложением.
- Тесты по одному, с паузами ([AGENTS.md](../../../../AGENTS.md)); красная проверка до правки.

## Что надо выяснить в разборе

- Формат таблицы в Каноне проекта (markdown-таблица или список с полями) и как его читает человек; границы (`id` уникальны, `required` по умолчанию истина).
- Что делать с шагами приёмки планов (`plan_acceptance`, `plan_merge_acceptance`): тот же механизм или отдельно.
- Как проекту-потребителю перенести свои шаги (миграция: один раз, по записи в журнале), не меняя его репозиторий из плагина.
